<p>「支持长连接」这句话很容易被理解成「永远在线」，于是有人配了心跳就以为万事大吉，直到某天发现任务跑了一半没有返回，日志里连报错都没有。长连接的几个误区都很隐蔽：断线不报错、心跳越勤反而越不稳、重连之后会话其实已经换了。这篇把四个最常见的误解挨个拆开，每个给出可观测的现象和改法，最后收敛成三条配置建议，适合正在跑持续对话或批量任务的团队对着自查。</p>

<h2>一、误区一：长连接等于永不断线</h2>
<p>长连接说的是「一次建立、多次复用」，不是「永不中断」。中间任何一环都可能把它掐掉。</p>
<h3>掐断连接的通常是中间设备</h3>
<p>家宽线路经过运营商 NAT，会话表有老化时间，常见在五到三十分钟；云侧的负载均衡也有空闲超时，通常六十秒到五分钟。两边任意一个先到，连接就被回收。客户端如果不主动刷新，下一次写入就会失败，而失败往往要等到超时才发现。</p>
<h3>为什么断线时看不到报错</h3>
<p>TCP 连接被中间设备单向回收时，两端可能都还认为连接有效。此时写入数据会进入「已发送但无回应」的状态，直到重传次数耗尽才报错，这个窗口短则几十秒，长则几分钟。表现就是「卡住」，而不是「断开」。</p>

<h2>二、误区二：心跳越勤越稳</h2>
<p>直觉上心跳频繁应该更稳，实际是把线路资源消耗在无效流量上。</p>
<h3>心跳的两个作用</h3>
<p>一是刷新 NAT 与会话表，让连接不被回收；二是尽早发现对端不可达。前者要求心跳间隔小于最短老化时间，后者要求间隔不要太长。两个作用对间隔的要求是相反的，取一个折中区间即可。</p>
<h3>常见的合理区间</h3>
<p>六十到一百二十秒之间。设成五秒不会更稳，只会让每条连接每分钟多出十几次小包，家宽上行本来就不宽裕，几十条连接叠加起来会把握手排队拉长，反而表现为「越用心跳越慢」。</p>
<h3>怎么测出自己的老化时间</h3>
<p>建一条连接后停止发送，用脚本每分钟写一次极小负载，记录第一次写入失败的时间点，重复三次取平均。这个数字就是你这条线路的实际老化时间，心跳间隔取它的三分之一到二分之一比较稳。</p>

<h2>三、误区三：断了重连就行，反正是同一个号</h2>
<img src="/tp.png" alt="Claude住宅IP长连接重连时的会话与出口核对">
<p>这是代价最大的一个误区。重连成功不等于会话延续。</p>
<h3>重连之后发生了什么</h3>
<p>新连接可能落到另一条出口、另一个节点，平台侧看到的是一次新的会话：来源地址变了、握手参数变了、有时连 TLS 指纹都不同。对持续对话类任务，这意味着上下文丢失；对批量任务，意味着已完成的进度需要重新确认，重复提交的风险随之上升。</p>
<h3>重连要带三样东西</h3>
<p>会话标识（能用上次的会话就复用）、同一出口段（不要跨段重连）、以及幂等键（防止重复提交）。三样里前两样减少异常判定，第三样减少业务侧损失。缺了第三样，重连一次可能就多提交一批数据。</p>
<p>重连次数也要有上限：无上限重连会形成一个循环：连上、失败、再连，每次都产生新的会话记录。建议单任务重连不超过三次，超过就降级为人工介入，并把当时的出口、返回码、时间点记录下来。</p>

<h2>四、误区四：所有任务都适合长连接</h2>
<p>长连接有明确的适用边界，越界使用会让简单问题复杂化。</p>
<h3>适合的：持续对话、长轮询、批量流式任务</h3>
<p>这几类任务的共同点是「一次会话内多次往返」，连接建立成本占比高，复用收益明显。特别是持续对话，连接重建会带来明显的等待感。</p>
<h3>不适合的：低频定时任务、一次性抓取</h3>
<p>一天跑几次的定时任务，维持长连接意味着二十多小时的空转心跳，收益几乎为零，还要承担断线不报错的风险。这类任务用短连接更直观：用完就断，有问题立刻暴露。</p>
<p>混合场景则要分开配置：同一个团队既有长会话又有短任务时，不要共用一套连接策略。长会话走保活路径，短任务走即用即断路径，两条路径的超时与重试参数分开设，混在一起会互相拖累。</p>

<h2>五、纠偏后的三条配置建议</h2>
<p>把上面四条反过来，就是三条可以直接落地的设置。</p>
<h3>建议一：心跳按实测老化时间的三分之一设</h3>
<p>不要照抄别人的数字。同一条线路在不同运营商、不同时段的老化时间都可能不同，实测一次只花半小时，比反复试错省事。</p>
<h3>建议二：把「连接存活」和「业务成功」分开监控</h3>
<p>连接活着但业务失败，是最难发现的状态。两个指标要分开采集：连接层的保活成功率、业务层的端到端成功率。两者出现背离时，问题通常在会话上下文或幂等处理上。</p>
<h3>建议三：断线要主动探测，不要等超时</h3>
<p>应用层加一个轻量探测，间隔与心跳错开，探测失败立即触发重连，而不是等业务请求超时。这一步能把「卡住三分钟」缩短到「十秒内恢复」。下面这张表是三条建议的对应关系，可以当验收清单用。</p>

<h2>常见问答</h2>
<h3>长连接会不会占用更多带宽？</h3>
<p>答：占用很少。心跳包通常只有几十字节，一小时几十次的量级可以忽略。真正占带宽的是业务数据，不是保活。反过来说，心跳设得过密时累加起来的无效流量也不小，几十条连接叠一起就明显了。</p>
<h3>断线后重连，账号会不会被要求验证？</h3>
<p>答：如果重连后出口段不变，通常不会；跨段重连相当于一次异地登录，验证概率明显上升。所以重连策略的第一原则是「留在同一段」，而不是「尽快连上」。</p>
<h3>心跳间隔设多少最稳？</h3>
<p>答：没有统一值。先实测这条线路的空闲老化时间，取三分之一到二分之一。多数家宽线路落在 60 到 120 秒之间，可以先按 90 秒试一周再微调。</p>
<h3>长连接适合跑批量任务吗？</h3>
<p>答：适合流式、持续的批量任务，不适合一天只跑一两次的定时任务。判断标准是一次任务内的往返次数，次数多的复用收益才明显。</p>
